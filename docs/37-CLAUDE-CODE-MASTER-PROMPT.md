# ▼ PROMPT — คัดลอกตั้งแต่บรรทัดนี้ลงไป

คุณกำลังทำงานกับ **บวรไทย** — ระบบ delivery ระดับตำบล ที่มีผู้ใช้จริงแล้ว
ไม่ใช่โครงการเปล่า **ห้ามสร้างใหม่ ให้ต่อยอดจากของเดิม**

## ก่อนแตะอะไรก็ตาม ให้ตรวจสี่แหล่งนี้ก่อน

1. `claude/36-PROJECT-CONSTITUTION-v2.0.md` — กฎหมายสูงสุด อ่านให้จบ
2. `claude/35-Master-Plan-และสถานะจริง.md` — สถานะจริงล่าสุด
3. **โค้ดและฐานข้อมูลจริง** — query เอง อ่านเอง ห้ามเชื่อเอกสารเก่าเรื่องข้อเท็จจริง
4. **สถานะ production จริง** — commit ล่าสุดที่ deploy แล้วคืออะไร
   ตรงกับ local ไหม secrets ตั้งครบหรือยัง

แหล่งที่ ๔ ถูกลืมบ่อยที่สุด และเป็นเหตุให้เชื่อว่าฟีเจอร์ใช้ได้แล้ว
ทั้งที่ผู้ใช้ยังไม่ได้อะไรเลย

## หกข้อที่ผิดบ่อยที่สุด — จำให้ได้

**๑. ชื่อในฐานข้อมูลชนะชื่อในเอกสารเสมอ**
ตารางจริงมี 19 ตาราง ดูรายชื่อใน Constitution หมวด ๑
`areas` ที่จริงคือ `tambons` · `riders` คือ `drivers` ·
`approval_requests` คือ `profiles.approved`
**ก่อนสร้างตารางใหม่ ต้องพิสูจน์ด้วย query ว่าไม่มีของเดิมทำหน้าที่นั้นอยู่**

**๒. `driver` ในโค้ด `ไรเดอร์` บนหน้าจอ**
แปลงคำที่ `ROLE_LABEL` ใน `src/lib/domain.ts` เท่านั้น
**ห้ามสร้างตารางแปลงคำชุดใหม่** ถ้าคิดว่าไม่มี ให้ `grep` ยืนยันแล้วรายงานก่อน
ห้ามเปลี่ยนชื่อ enum หรือตาราง

**๓. สิทธิ์ตัดสินที่ฐานข้อมูลเท่านั้น**
ใช้ `can_admin_profile()`, `can_admin_tambon()`, `my_tambon_id()`,
`has_national_scope()`, `is_approved_driver_in()`
**ห้ามเขียนตรรกะสิทธิ์ซ้ำในโค้ดแอปหรือ n8n**
**การเช็คฝั่งเบราว์เซอร์มีไว้เพื่อ UX ไม่ใช่ความปลอดภัย** —
ซ่อนปุ่มไม่ให้ผู้ใช้สับสน ไม่ใช่กันคนที่ตั้งใจจะเข้า

**๔. migration ต้องครบสี่คุณสมบัติ**
`VERSIONED` อยู่ในไฟล์ · `REPRODUCIBLE` สร้างจากศูนย์ได้ ·
`RECOVERABLE` มีแผนกู้เขียนไว้ก่อน apply · `IDEMPOTENT` รันซ้ำไม่พัง
apply อย่างเดียวโดยไม่เขียนไฟล์ = ละเมิด เพราะตำบลที่ ๒ จะสร้างไม่ได้
`security definer` ต้องปัก `search_path` + `revoke` จาก `anon, authenticated`

**๕. `TASK COMPLETE` ไม่เท่ากับ `FEATURE LIVE`**
```
TASK COMPLETE  = เขียน + ทดสอบ + มีหลักฐาน + ของเดิมไม่พัง
FEATURE LIVE   = TASK COMPLETE + deploy แล้ว + ตรวจบน production แล้ว
```
รายงาน `TASK COMPLETE` ลอย ๆ ไม่ได้ — ต้องบอกด้วยเสมอว่า
**เหลืออะไรก่อนถึง FEATURE LIVE และใครต้องทำ**
ห้ามใช้คำว่า "เรียบร้อยแล้ว" กับงานที่ยังไม่ live

**๖. ฐานข้อมูลไม่มี rollback**
โค้ดถอยได้ (`git revert` + deploy) แต่ฐานข้อมูลที่มีข้อมูลผู้ใช้อยู่แล้ว
ค่าตั้งต้นคือ **แก้เดินหน้า** การเลิกใช้คอลัมน์ทำสองจังหวะเสมอ
(เลิกอ่านก่อน → ค่อยลบทีหลัง)

## จัดระดับงานก่อนลงมือทุกครั้ง

| ระดับ | คืออะไร | ต้องทำ |
|---|---|---|
| A | เอกสาร | ทำได้เลย |
| B | หน้าจอ ไม่แตะข้อมูล | ทำได้ + ต้องทดสอบ |
| C | ตรรกะแอป | รายงานผลกระทบก่อน |
| D | migration | รายงาน + แผนกู้ |
| E | สิทธิ์ / RLS / auth | **หยุด ขออนุมัติ** |
| F | ทำลายได้ / แตะข้อมูลผู้ใช้จริง | **หยุด ขออนุมัติ** |

ไม่แน่ใจ = ถือว่าระดับสูงกว่า · งานที่พาดหลายระดับ = ยึดระดับสูงสุด
**งานที่จะขึ้น production ต้องรายงานผลกระทบต่อผู้ใช้เพิ่มเสมอ ไม่ว่าระดับไหน**

## ลำดับการทำงาน

```
อ่าน → ตรวจของจริง → จัดระดับ → SESSION START REPORT → ลงมือ → ทดสอบ → รายงาน
```

## ก่อนลงมือ ให้ส่ง SESSION START REPORT

```
งาน:
ระดับ (A–F):
หลักฐานที่ตรวจแล้ว:     (ระบุว่า query อะไร อ่านไฟล์ไหน — ไม่ใช่แค่ติ๊ก)
  · Constitution
  · สถานะล่าสุด
  · โค้ด / ฐานข้อมูล
  · สถานะ production
ส่วนที่กระทบ:
ความเสี่ยงที่รู้อยู่:
แผน: ๑. ๒. ๓.
```

**หลักฐานไม่พอ หรือระดับ E/F → หยุดรอคำอนุมัติ ห้ามลงมือ**

**Stop Rule:** ถ้าแก้จุดเดียวแล้วต้องแตะอีกสิบจุด ให้หยุดรายงานก่อน
นั่นแปลว่าเข้าใจปัญหาผิด ไม่ใช่ว่าต้องขยันขึ้น
*ยกเว้น* เมื่อเกิดจาก contract เดียวกันที่เปลี่ยนจริง — กรณีนั้นส่งรายการ
จุดที่กระทบทั้งหมดก่อนลงมือ ไม่ใช่ทยอยค้นพบระหว่างทาง

## เมื่อเอกสารขัดกับระบบจริง

**ห้ามแก้ระบบตามเอกสารทันที** ให้รายงานพร้อมหลักฐาน แล้วรอคำตัดสิน

- **ชื่อ/ตัวเลขไม่ตรง** → เอกสารมักผิด
- **หลักการไม่ตรง** → ห้ามสรุปว่าโค้ดผิด อาจเป็นการตัดสินใจของเจ้าของโครงการ
  ที่ยังไม่ได้บันทึก หรือข้อจำกัดทางเทคนิคที่เอกสารไม่รู้ — เสนอทั้งสามทาง
  แล้วให้เจ้าของเลือก

AI ที่เจอชื่อไม่ตรงแล้ว "แก้ระบบตามเอกสาร" คือ AI ที่กำลังจะสร้างตารางซ้ำ

## ห้ามเด็ดขาด

- ปิดหรือลดความเข้ม RLS เพื่อให้โค้ดทำงานได้
- ย้ายตรรกะสิทธิ์ไปฝั่งหน้าเว็บ
- เขียน secret ลงโค้ดหรือ commit เข้า git
- ถือโอกาส refactor / rename / upgrade package ไปพร้อมกับงานอื่น
- แตะ `package.json` โดยไม่มีเหตุผลที่ระบุได้
- รายงานว่าเสร็จทั้งที่ยังไม่ครบนิยาม
- **เงียบเรื่องที่ทำพลาด** — ถ้ารู้ว่าเคยบอกผิด ต้องแก้ทันทีก่อนทำอย่างอื่น

## วิธีรายงานเมื่อจบงาน

บอกให้ครบสี่อย่าง สั้น ๆ:
1. ทำอะไรไป (ระดับ A–F) — `TASK COMPLETE` หรือ `FEATURE LIVE`
2. ทดสอบอะไร ได้ผลอะไร — ถ้าไม่ได้ทดสอบ ให้บอกว่าไม่ได้ทดสอบ
3. **สิ่งที่ยังไม่ได้ทำ และสิ่งที่อาจพัง**
4. ต้องให้เจ้าของโครงการทำอะไรต่อ ก่อนผู้ใช้จะได้ประโยชน์

ห้ามสรุปว่า "เรียบร้อยแล้ว" ถ้ายังมีข้อ 3 หรือข้อ 4

## หมายเหตุถึงเจ้าของโครงการ

**Prompt นี้ไม่ได้แทน Constitution** มันบังคับให้ AI ไปอ่าน Constitution
ถ้าตัดขั้นตอนการอ่านออกเพื่อประหยัดเวลา กฎทั้งหมดจะหายไปพร้อมกัน

**SESSION START REPORT คือกลไกที่ให้ผลตอบแทนสูงที่สุดในเอกสารนี้**
เพราะมันทำให้คุณเห็นว่า AI เข้าใจระบบถูกหรือผิด **ก่อน** มันแตะอะไร
การอ่านรายงานหกบรรทัดถูกกว่าการตามแก้โค้ดที่สร้างจากความเข้าใจผิดเสมอ
ถ้าหลักฐานในรายงานเป็นแค่การติ๊กโดยไม่ระบุว่า query อะไร ให้ถือว่ายังไม่ได้ตรวจ

**เมื่อเกิดความผิดพลาดใหม่ ให้เพิ่มเข้า Constitution ก่อน แล้วค่อยพิจารณาว่า
ควรยกขึ้นมาไว้ใน Prompt นี้ไหม** — Prompt นี้ควรมีแต่ข้อที่ผิดบ่อยที่สุด
ถ้ามันยาวขึ้นเรื่อย ๆ มันจะเริ่มไม่ได้ผล

**ข้อที่ ๕ เป็นข้อที่ผิดง่ายที่สุด** เพราะฟังดูไม่สำคัญ
แต่ขณะที่เขียนเอกสารนี้ มีงานอยู่ 4 commit ที่ `TASK COMPLETE` แล้ว
แต่ยังไม่ `FEATURE LIVE` — ผู้ใช้บุ่งไหมยังใช้ระบบของวันที่ 5 ก.ย. อยู่
