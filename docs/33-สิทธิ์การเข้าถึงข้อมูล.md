# สิทธิ์การเข้าถึงข้อมูล — ใครเห็นอะไรได้บ้าง

*อัปเดต 5 กันยายน 2569 — ใช้จริงบนฐานข้อมูลแล้ว*

## ปัญหาที่แก้

เดิม policy ของ `profiles` `drivers` `merchants` ใช้ `USING (true)` และ `orders`
เปิดให้อ่านงานสถานะ `pending` ได้ทุกตำบล ผลคือ **ผู้ใช้ที่ล็อกอินคนเดียว
อ่านชื่อ เบอร์โทร พร้อมเพย์ และ LINE ID ของคนทั้งประเทศได้**

ตอนที่ยังต้องสมัครด้วยรหัสผ่านและรอตัวแทนตำบลอนุมัติ ความเสี่ยงยังจำกัด
แต่พอเปิด LINE Login ให้สาธารณะ ใครก็ตามที่มี LINE กดปุ่มเดียวก็เป็น
`authenticated` แล้วอ่านได้ทันที เป็นเรื่อง PDPA ตรง ๆ

อีกจุด: `is_admin()` ไม่ผูกกับตำบล **ตัวแทนตำบลจึงมีสิทธิ์เท่าส่วนกลาง**
เห็นและแก้ข้อมูลทุกตำบล ซึ่งไม่ตรงกับที่ออกแบบไว้

## กติกาปัจจุบัน

**profiles** — เห็นได้เมื่อ เป็นตัวเอง · เคยอยู่ในออเดอร์เดียวกัน (ลูกค้า↔ไรเดอร์↔ร้าน)
· เป็นแอดมินของตำบลที่คนนั้นสังกัด

**orders** — ลูกค้าเจ้าของ · ไรเดอร์ที่รับงาน · ร้านที่เกี่ยวข้อง ·
**ไรเดอร์ที่อนุมัติแล้วในตำบลเดียวกัน** (เฉพาะงาน `pending`) · แอดมินของตำบลนั้น

**drivers / merchants** — ตัวเอง · คนที่อยู่ในออเดอร์เดียวกัน · แอดมินของตำบล
(ร้านที่ `is_open = true` ยังเห็นได้ทั่วไป เพราะเป็นข้อมูลหน้าร้าน)

**plots (แปลงเกษตร)** — เจ้าของ · แอดมินของตำบล · ผู้ให้บริการที่อนุมัติแล้วในตำบลนั้น

**tambons** — แก้ไขได้เฉพาะแอดมินของตำบลนั้น (เดิมแก้ข้ามตำบลได้)

## ผู้ช่วยส่วนกลาง — เตรียมไว้แล้ว

ทำเป็นตาราง `admin_scopes` แทนการเพิ่ม role ใหม่ใน enum เพราะผู้ช่วยในอนาคต
อาจดูแล **บางตำบล** ไม่ใช่ทั้งประเทศเสมอไป

```
admin_scopes (profile_id, tambon_id, note, granted_by, created_at)
```

- หนึ่งแถว = สิทธิ์ดูแลหนึ่งตำบล
- `tambon_id` ว่าง = สิทธิ์ระดับประเทศ
- ถอนสิทธิ์ = ลบแถว
- **มอบและถอนได้เฉพาะคนที่มีสิทธิ์ระดับประเทศ** ตัวแทนตำบลตั้งผู้ช่วยเองไม่ได้

ทดสอบแล้ว: มอบสิทธิ์รายตำบลให้โปรไฟล์ทดสอบ → เห็นข้อมูลในตำบลนั้นได้
แต่ `has_national_scope` ยังเป็น false ถูกต้อง (ลบแถวทดสอบออกแล้ว)

## ฟังก์ชันที่ใช้ตัดสิน

ทุกตัวเป็น `security definer` และปักหมุด `search_path` — จำเป็น เพราะถ้าไม่ทำ
policy ที่เรียกฟังก์ชันจะวนอ่านตารางเดิมจนเกิด infinite recursion

| ฟังก์ชัน | ตอบคำถาม |
|---|---|
| `has_national_scope()` | เป็นส่วนกลาง หรือผู้ช่วยระดับประเทศไหม |
| `can_admin_tambon(t)` | ดูแลตำบลนี้ได้ไหม |
| `can_admin_profile(p)` | ดูแลคนคนนี้ได้ไหม (ดูจากตำบลที่เขาสังกัด) |
| `is_approved_driver_in(t)` | เป็นผู้ให้บริการที่อนุมัติแล้วในตำบลนี้ไหม |
| `shares_order_with(p)` | เคยอยู่ในออเดอร์เดียวกันคนละฝั่งไหม |
| `my_tambon_id()` | ตำบลของตัวเอง |

`is_admin()` ยังอยู่เพื่อความเข้ากันได้กับโค้ดเก่า ความหมายใหม่คือ
"เป็นแอดมินระดับใดก็ได้" — **ห้ามใช้ตัดสินขอบเขต** ให้ใช้ตัวที่ผูกตำบลแทน

## ข้อควรระวังเมื่อเขียนหน้าใหม่

หน้าแอดมินทั้งหมดใช้ `select("*")` โดยไม่กรองตำบลเอง — **ขอบเขตมาจาก RLS ล้วน ๆ**
ข้อดีคือแก้ที่เดียวได้ผลทุกหน้า ข้อเสียคือถ้าเผลอเขียน policy หลวมเมื่อไหร่
ทุกหน้ารั่วพร้อมกันทันที ตอนเพิ่มตารางใหม่จึงต้องเขียน policy ให้ครบเสมอ

ตารางที่เปิด RLS แต่ยังไม่มี policy เลย (`ai_conversations` `job_seekers`
`pending_menu_items`) อ่านไม่ได้เลยผ่าน PostgREST — ปลอดภัยไว้ก่อน
แต่แปลว่าฟีเจอร์ที่ใช้ตารางเหล่านี้ยังทำงานไม่ได้
