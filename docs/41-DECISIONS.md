# ๔๑ — บันทึกการตัดสินใจ (ADR)

> ทำไมระบบถึงเป็นแบบนี้ — เพื่อให้อีกหกเดือนข้างหน้าไม่มีใครรื้อของที่ตั้งใจทำไว้
> รูปแบบ: **บริบท → ตัดสินใจ → เหตุผล → ผลที่ตามมา → สถานะ**
>
> สถานะมีสามค่า: **ตัดสินแล้ว** · **รอเจ้าของโครงการตัดสิน** · **ยกเลิกแล้ว** (ต้องบอกว่า ADR ไหนแทน)

---

## ADR-001 — Supabase คือความจริงของระบบ

**บริบท:** ระบบมีทั้ง PWA, n8n และ LINE เขียนข้อมูลได้

**ตัดสินใจ:** ฐานข้อมูล Supabase เป็นแหล่งความจริงเดียว · ห้ามให้ระบบใดเก็บสถานะคู่ขนาน

**เหตุผล:** ต้องตรวจสอบย้อนหลังได้ทุกรายการ และการมีสองแหล่งความจริงคือการรับประกันว่า
วันหนึ่งมันจะไม่ตรงกัน โดยไม่มีใครรู้ว่าอันไหนถูก

**สถานะ:** ตัดสินแล้ว

---

## ADR-002 — สิทธิ์ตัดสินที่ฐานข้อมูล

**ตัดสินใจ:** ตรรกะสิทธิ์อยู่ใน RLS และฟังก์ชันของฐานข้อมูลเท่านั้น
(`can_admin_profile()`, `can_admin_tambon()`, `my_tambon_id()`, `is_approved_driver_in()`)

**ผลที่ตามมา:** การเช็คสิทธิ์ฝั่งเบราว์เซอร์มีไว้เพื่อ UX — ซ่อนปุ่มไม่ให้ผู้ใช้สับสน
**ไม่ใช่ความปลอดภัย** ใครก็ยิง PostgREST ตรงได้

**สถานะ:** ตัดสินแล้ว

---

## ADR-003 — `driver` ในโค้ด `ไรเดอร์` บนหน้าจอ

**ตัดสินใจ:** ชื่อในฐานข้อมูลและโค้ดคือ `driver` ถาวร · คำที่ผู้ใช้เห็นคือ "ไรเดอร์"
แปลงที่ `ROLE_LABEL` ใน `src/lib/domain.ts` **ที่เดียว**

**เหตุผล:** การเปลี่ยนชื่อ enum หรือตารางในระบบที่มีข้อมูลผู้ใช้แล้ว มีต้นทุนสูงกว่าประโยชน์เสมอ

**สถานะ:** ตัดสินแล้ว

## ADR-004 — ค่อย ๆ ดึงอำนาจออกจาก n8n ไม่ใช่ย้ายทั้งระบบ

**ตัดสินแล้ว 11 ก.ย. 2569 โดยเจ้าของโครงการ**

### คำตัดสิน

> โครงการจะ **ไม่รื้อ `My workflow 3`** และไม่ย้ายระบบออกจาก n8n แบบครั้งเดียวจบ
> เพราะ workflow นี้คือระบบที่ผ่านการใช้งานจริงแล้ว — **34 ออร์เดอร์ จากคน 9 คน**
>
> **n8n คงบทบาท Orchestration Authority** — แจ้งเตือน · ประสานระบบ · บทสนทนา · สรุปรายวัน · อันดับ · ผู้ช่วย AI
>
> **Supabase เป็น Core Authority** — ตัวตน · สิทธิ์ · การอนุมัติ · เงิน · ledger · สถานะออร์เดอร์ · กฎธุรกิจที่กระทบความปลอดภัย
>
> การย้ายทำทีละก้อน แต่ละก้อนต้องมีหลักฐาน · การทดสอบ · แผนกู้ · และการตรวจบน production
>
> **ห้ามเปลี่ยนสิ่งที่ทำงานจริงเพียงเพื่อให้ตรงกับเอกสาร**
> **ห้าม refactor 158 node แบบกว้างโดยไม่มีแผนที่การพึ่งพา**

### ทิศทางที่ต่างจากเดิม

```
ตอนนี้:  LINE → n8n (ถือ service key) → เขียน Supabase ข้าม RLS → ตอบ LINE
         n8n เป็นทั้งผู้ตัดสิน ฐานข้อมูล และระบบสิทธิ์ในตัวเดียว

เป้าหมาย: LINE / PWA → เรียก Supabase RPC → RPC ตรวจ user · สิทธิ์ · ออร์เดอร์ ·
          ยอดเงิน · กฎธุรกิจ → COMMIT → เกิด event → n8n แจ้งคนที่เกี่ยวข้อง

ประโยคเดียว: ฐานข้อมูลตัดสิน → n8n ดำเนินการต่อ
```

**หมายเหตุจาก AI (แก้จากผังที่เสนอมา):** ผังต้นฉบับมีชั้น "Core Backend" แยกออกมา
แต่ระบบจริง**ไม่มีชั้นนั้นและไม่ควรสร้าง** — แอป Next.js คือ backend เดียวที่มี
และจุดบังคับกฎคือ **Supabase RPC + RLS** ทั้งแอปและ n8n เป็นเพียง *ผู้เรียก*
การเพิ่มชั้นใหม่ขัดกับหลัก "อย่าสร้างใหม่" ของ ADR นี้เอง

### ลำดับการย้าย

| เฟส | ทำอะไร | สถานะ |
|---|---|---|
| **A** | **Audit** — ทำแผนที่ว่า node ไหนเขียนอะไร ใช้สิทธิ์ระดับไหน | ทำแล้ว รอบแรก → `44-N8N-AUDIT.md` |
| **B** | ย้าย **ตัวตน → สิทธิ์ → เงิน** ออกจาก n8n | ถัดไป |
| **C** | ย้ายการเปลี่ยน **สถานะออร์เดอร์** ไปเป็น DB RPC | รอ B |
| **D** | ลดขอบเขต service key ให้เหลือเท่าที่จำเป็น | รอ C |

### ⚠️ ข้อเดียวที่ AI ขอปรับจากข้อเสนอ — ลำดับใน Phase B

ข้อเสนอเดิมเรียง **เงิน → สิทธิ์ → ตัวตน** · ขอสลับเป็น **ตัวตน → สิทธิ์ → เงิน**

**เหตุผล ๒ ข้อ:**

1. **ตัวตนคือเรื่องเดียวที่กำลังสร้างความเสียหายอยู่ตอนนี้** — โปรไฟล์ที่ล็อกอินไม่ได้
   เพิ่มขึ้นทุกครั้งที่มีคนใหม่ทัก LINE ส่วนเงินยังไม่มีบาทเดียวไหลผ่านระบบ
   จึงดูเร่งด่วนแต่ยังไม่เลือดออก
2. **อีกสองเรื่องตั้งอยู่บนตัวตน** — การตรวจสิทธิ์ที่ถูกต้อง และแถว ledger ที่ถูกต้อง
   เป็นไปไม่ได้เลยสำหรับผู้ใช้ที่ไม่มีบัญชี `auth.users` การย้ายเงินก่อนตัวตน
   คือการสร้างบัญชีการเงินให้คนที่ระบบยังระบุตัวไม่ได้

### PWA อยู่ตรงไหน

**ยอมรับข้อมูลจริง: LINE คือช่องทาง production วันนี้ (34 ออร์เดอร์) · PWA คือช่องทางที่กำลังโต (2)**
ไม่ประกาศให้ PWA เป็นระบบหลักทั้งที่ผู้ใช้ยังไม่ใช้ — แต่สถาปัตยกรรมระยะยาว
ทั้งสองช่องทางเรียก Core Authority เดียวกัน

**การค้นหาอาหารไม่อยู่ใน ADR นี้** — เป็นงานถัดไป (ดู ADR-007, ADR-008 และเอกสาร ๓๘)

## ADR-005 — ทางเข้าระบบขึ้นกับวิธีล็อกอิน ไม่ใช่บทบาท

**ตัดสินใจ:** หน้าหลังบ้าน (ไรเดอร์ · ร้าน · ตัวแทนตำบล · ส่วนกลาง) ต้องเข้าด้วยรหัสผ่าน
ปุ่ม LINE เข้าได้ทุกคน แต่เห็นเฉพาะหน้าบ้าน

**เหตุผล:** ปุ่ม LINE กดครั้งเดียวติด มือถือที่ปลดล็อกอยู่แล้วถูกหยิบไปกดก็เข้าได้
จึงเป็นปัจจัยที่อ่อนกว่ารหัสผ่าน และไม่ควรเปิดหน้าที่มีเงินให้

**วิธี:** `session_used_password()` อ่าน `auth.mfa_amr_claims` ของ session นั้น
ไม่เดาจากอีเมลของบัญชี เพราะคนที่ผูก LINE กับบัญชีที่สมัครด้วยเบอร์มีทั้งสองทาง

**ค้าง:** ยังคุมที่หน้าเว็บอย่างเดียว ยังไม่ล็อกที่ระดับ RLS

**สถานะ:** ตัดสินแล้ว (ยังทำไม่ครบ)

## ADR-006 — AI ช่วยเข้าใจลูกค้า ฐานข้อมูลเป็นความจริง

**ตัดสินใจ:** AI แปลประโยคเป็นคำค้นได้ **ห้าม AI ตอบว่าร้านไหนมีอะไร ราคาเท่าไร หรือเปิดอยู่ไหม**
ข้อมูลเหล่านั้นต้องมาจาก query เท่านั้น

**เหตุผล:** AI ที่แต่งชื่อร้านหรือราคาขึ้นมาเอง สร้างความเสียหายกับร้านจริงในตำบล
และเป็นความเสียหายที่กู้คืนไม่ได้ด้วยการแก้โค้ด

**สถานะ:** ตัดสินแล้ว

## ADR-007 — ค้นภาษาไทยด้วย `ilike` ไม่ใช่ full-text

**ตัดสินใจ:** ค้นชื่อสินค้าด้วย `ilike '%คำ%'` · ถอดคำนำ/ท้ายด้วยรายการคำในโค้ด ไม่เรียก LLM

**เหตุผล:** ภาษาไทยไม่มีช่องว่างระหว่างคำ Postgres ตัดคำไทยไม่ได้ `to_tsvector('thai', …)`
ไม่มีในมาตรฐาน · และที่ปริมาณสินค้าระดับตำบล การเรียก LLM ทุกครั้งที่มีคนทัก
เสียเงินและช้าขึ้น 2–3 วินาที โดยแลกความแม่นยำมาได้น้อยมาก

**ผลข้างเคียงที่ยอมรับ:** ค้น "ชา" จะเจอ "ถ่านไบโอ**ชา**ร์" ด้วย
ทางแก้ในอนาคตคือตารางคำพ้อง ไม่ใช่ full-text

**สถานะ:** ตัดสินแล้ว

## ADR-008 — เมนูของร้านที่เปิดอยู่เป็นข้อมูลสาธารณะ

**ตัดสินใจ:** `search_menu()` เป็น `security definer` และให้ `anon` เรียกได้
คืนเฉพาะร้านที่เปิดอยู่ · สินค้าที่ยังขายและไม่ถูกซ่อน · เฉพาะคอลัมน์ที่ต้องแสดง

**ทางที่ไม่เลือก:** เปิด policy ให้ `anon` อ่าน `menu_items` ทั้งตาราง (กว้างเกิน จะเห็นเมนูร้านที่ปิด
และเมนูที่ร้านสั่งซ่อน) · ใช้ service key ในฝั่ง webhook (ให้อำนาจข้าม RLS ทั้งหมดเพื่องานอ่านชิ้นเดียว)

**เหตุผล:** คนที่ทัก LINE OA มายังไม่ได้สมัครก็ได้ ซึ่งเป็นหัวใจของฟีเจอร์
และป้ายเมนูหน้าร้านก็ใครเดินผ่านก็อ่านได้อยู่แล้ว

**ตรวจแล้วว่าไม่กว้างเกิน:** ในฐานะ `anon` เรียก `search_menu()` ได้ผลลัพธ์ปกติ
แต่ `select from menu_items` ตรง ๆ ยังได้ 0 แถว

**สถานะ:** ตัดสินแล้ว · apply เมื่อ 10 ก.ย. 2569

## ADR-009 — เงิน สิทธิ์ และตัวตน บังคับที่ฐานข้อมูล ไม่ใช่ที่ n8n และไม่ใช่ที่ PWA

**สถานะ: ตัดสินไปแล้วตั้งแต่ 9 ก.ย. 2569 — อยู่ในธรรมนูญ หมวด ๘**

เรื่องนี้ไม่ต้องตัดสินใหม่ ธรรมนูญเขียนไว้แล้วเกือบทุกคำ:

- **กฎ ๘.๑** Supabase PostgreSQL คือความจริงเพียงหนึ่งเดียว — หน่วยความจำของ n8n ไม่ใช่ความจริง
- **กฎ ๘.๒ / ๘.๒.๑** frontend ไม่ใช่ผู้ตัดสินสิทธิ์ · การเช็คฝั่งเบราว์เซอร์มีไว้เพื่อ UX ไม่ใช่ความปลอดภัย
- **กฎ ๘.๓** n8n ทำหน้าที่ประสานงาน ไม่ใช่เจ้าของความจริง และไม่ใช่ผู้ถือ lock — งานที่ต้อง atomic ต้องอยู่ใน PostgreSQL transaction
- **กฎ ๘.๔** AI ให้คำแนะนำ ไม่ใช่ผู้มีอำนาจตัดสิน

**ปัญหาจึงไม่ใช่ "ยังไม่มีกฎ" แต่คือ "มีกฎแล้วแต่ระบบยังไม่ทำตาม"**

**เพิ่มเมื่อ 10 ก.ย. 2569:** ช่องโหว่เดียวที่หมวด ๘ ยังไม่ครอบคลุมคือ *สิ่งที่ฐานข้อมูล
บังคับเองไม่ได้* (สร้างบัญชีผู้ใช้ · เรียก API ภายนอก) จึงเพิ่ม **กฎ ๘.๗** พร้อมรายชื่อ
บริการที่ถือกุญแจระดับสูง — ซึ่งเปิดเผยว่า n8n ถือ secret key ที่เขียนได้ทุกตาราง
โดยไม่เคยมีใครบันทึกไว้ที่ไหน

ADR-004 จึงถูกตีกรอบผิดตั้งแต่แรก คำถามไม่ใช่ *"n8n หรือแอปควรเป็นเจ้าของ"*
แต่คือ **"จะทำให้ความจริงตรงกับกฎที่มีอยู่แล้วได้อย่างไร"**

## ADR-010 — กฎเขียนไว้ไม่พอ ถ้าทำเป็น constraint ได้ ต้องทำ

**บริบท:** ธรรมนูญห้าม n8n เป็นเจ้าของความจริงมาตั้งแต่ 9 ก.ย. แต่วันที่ 10 ก.ย.
ยังมีโปรไฟล์ที่ไม่มีบัญชี auth เพิ่มขึ้นเรื่อย ๆ เพราะไม่มีอะไร**ห้าม**มันได้จริง

**หลักฐาน (ตรวจ 10 ก.ย. 2569):** ตาราง `profiles` มี foreign key เดียวคือไปที่ `tambons`

```sql
profiles_tambon_id_fkey  FOREIGN KEY (tambon_id) REFERENCES tambons(id)
```

**ไม่มี FK จาก `profiles.id` ไปที่ `auth.users.id`** ฐานข้อมูลจึงยอมรับโปรไฟล์ที่ไม่มีบัญชีจริง
โดยไม่บ่นสักคำ — นี่คือเหตุผลเชิงโครงสร้างของบั๊กที่ทำให้คน 6 คนล็อกอินไม่ได้

**ตัดสินใจ:** เมื่อกฎข้อไหนแปลงเป็น constraint ของฐานข้อมูลได้ **ต้องแปลง**
กฎที่เขียนไว้เฉย ๆ บังคับได้เฉพาะกับคนที่อ่าน ส่วน constraint บังคับได้กับทุกคน
รวมทั้ง workflow ที่ถือ service key และ AI ที่ไม่เคยอ่านเอกสาร

**สิ่งที่เสนอ:**

```sql
alter table public.profiles
  add constraint profiles_id_fkey
  foreign key (id) references auth.users(id) on delete cascade;
```

**⚠️ ห้าม apply ลำพัง — จะทำให้การสมัครสมาชิกทาง LINE พังทันที**

ลำดับที่ถูกต้อง:

1. ล้างโปรไฟล์ที่ไม่มีบัญชีออกก่อน (ไม่งั้น `alter table` ล้มเหลว)
2. สร้างทางสมัครสมาชิกที่สร้างบัญชี auth ให้ครบ แล้วให้ n8n เรียกทางนั้นแทนการเขียนตารางตรง
3. ทดสอบคู่ขนานจนแน่ใจ
4. **ค่อย** เพิ่ม FK เป็นตัวปิดประตูถาวร

หลังข้อ 4 การสร้างโปรไฟล์ผีจะเป็นไปไม่ได้เชิงกายภาพ ไม่ใช่แค่ผิดกฎ

**สถานะ:** หลักการ **อนุมัติแล้ว 10 ก.ย. 2569** — เขียนเป็น **กฎ ๘.๖** ในธรรมนูญ v2.3
ส่วนการเพิ่ม FK จริงยังรออนุมัติแยก (งานชั้น F — แตะข้อมูลผู้ใช้จริง) และต้องทำตามลำดับ ๔ ขั้นข้างบน

## ADR-011 — เงินต้องเป็นบัญชีเดินสะพัด ไม่ใช่ตัวเลขยอดคงเหลือ

**บริบท:** ระบบวันนี้ **ยังไม่มีกระเป๋าเงิน ไม่มียอดคงเหลือ ไม่มีตาราง `wallets`**
`orders` เก็บ `items_subtotal` `delivery_fee` `price` `payment_method` และเก็บเงินปลายทาง
(ธรรมนูญ กฎ ๙.๓)

**จึงเป็นเวลาที่ถูกที่สุดที่จะตัดสินเรื่องนี้ — ก่อนบาทแรกจะไหลผ่านระบบ**

**ตัดสินใจ:** เมื่อถึงวันที่มีเงินอยู่ในระบบ

- **บัญชีเดินสะพัด (ledger) ที่เพิ่มได้อย่างเดียว คือหลักฐานทางการเงิน**
- **ยอดคงเหลือเป็นค่าที่คำนวณมาจาก ledger** — เป็นแคชเพื่อความเร็ว ไม่ใช่ความจริง
- ห้ามมีโค้ดที่ "อ่านยอด → ลบ → เขียนยอดกลับ" ไม่ว่าที่ไหน
  การหักเงินทุกครั้งต้องเป็นการเพิ่มแถวใน ledger ภายใน transaction เดียว
- **ห้าม n8n เป็นผู้เขียน ledger**

**เหตุผล:** ยอดคงเหลือที่แก้ทับไปเรื่อย ๆ เมื่อผิดแล้วจะไม่มีทางรู้ว่าผิดตั้งแต่เมื่อไร
ส่วน ledger บอกได้เสมอว่าเงินมาจากไหนและหายไปตอนไหน — และระบบนี้จะต้องมี
ส่วนแบ่งของร้าน ไรเดอร์ และตัวแทนตำบลอยู่ในกระเป๋าเดียวกัน
