# หมวด ๑ — ชื่อที่ผูกไว้แล้ว (BOUND NAMES)

> **นี่คือหมวดที่สำคัญที่สุด และเป็นหมวดที่ Master Guide v2.0 ยังขาด**
>
> v2.0 บอกว่า "ห้ามสร้างตารางซ้ำ" แต่ในเวลาเดียวกันก็เสนอชื่อ Domain
> แบบทั่วไป (`areas`, `area_representatives`, `approval_requests`) พร้อม
> หมายเหตุว่า "ต้องตรวจชื่อจริงก่อน" — ซึ่งขัดกันเอง เพราะ AI ที่อ่านแล้ว
> ไม่ได้ตรวจ จะสร้างตารางใหม่ตามชื่อที่เห็นทันที

**หมวดนี้อยู่เหนือชื่อทุกชื่อใน Master Guide ทุกฉบับ ทุกเวอร์ชัน**
ไม่ต้องแก้ Master Guide ให้ชื่อตรง — เมื่อขัดกัน ให้ยึดหมวดนี้เสมอ

## ๑.๑ ตารางที่มีอยู่จริง (ตรวจเมื่อ 2026-09-09) — ห้ามสร้างซ้ำ

```
admin_actions        admin_scopes         ai_conversations
drivers              job_seekers          menu_items
merchants            order_events         order_items
orders               pending_menu_items   places
plots                profiles             ratings
tambon_applications  tambon_profiles      tambons
web_applications
```

**การจับคู่กับศัพท์ใน Master Guide (CANONICAL DATABASE NAME):**

| Master Guide เรียก | ชื่อจริงที่ต้องใช้ |
|---|---|
| `areas` | `tambons` |
| `area_representatives` | `profiles.role = 'admin'` + `admin_scopes` |
| `approval_requests` | `profiles.approved` (boolean) + `tambon_applications` |
| `riders` | `drivers` |
| Community Trust | `profiles.approved` ที่ตัวแทนตำบลกดอนุมัติ |

**กฎ:** ก่อนสร้างตารางใหม่ ต้องพิสูจน์ว่าไม่มีตารางใดในรายการข้างบน
ทำหน้าที่นั้นอยู่แล้ว การพิสูจน์ต้องอ้าง query จริง ไม่ใช่การอ่านเอกสาร

## ๑.๒ ค่า enum ที่ผูกไว้ — เปลี่ยนไม่ได้โดยไม่มี migration ที่อนุมัติแล้ว

```
order_status : pending · accepted · in_progress · delivered · cancelled
user_role    : customer · driver · merchant · admin · superadmin
order_type   : food · parcel · ride · agri_service
```

## ๑.๓ ฟังก์ชันสิทธิ์ที่เป็นผู้ตัดสินเพียงผู้เดียว

```
my_tambon_id()            has_national_scope()      is_admin()
can_admin_tambon(t)       can_admin_profile(p)      is_approved_driver_in(t)
shares_order_with(p)      is_superadmin()           is_tambon_admin(t)
```

**กฎ:** ห้ามเขียนตรรกะสิทธิ์ซ้ำในโค้ดแอปหรือใน n8n
โค้ดที่ต้องตัดสินสิทธิ์ ต้องถามฟังก์ชันเหล่านี้
กฎสองชุดที่ต้องตรงกันตลอดไป คือกฎที่จะไม่ตรงกันสักวัน

## ๑.๔ จุดแปลงคำเป็นภาษาไทย — มีที่เดียว

```
src/lib/domain.ts
  ROLE_LABEL     ← บทบาท
  STATUS_LABEL   ← สถานะออเดอร์
  TYPE_LABEL     ← ประเภทงาน
  VEHICLE_LABEL  ← ประเภทรถ
```

**กฎ:** ต้องใช้ตารางแปลงคำที่มีอยู่แล้วเท่านั้น
**ห้ามสร้างตารางแปลงคำชุดใหม่ที่อื่น** ถ้าคิดว่าไม่มีอยู่จริง ให้ยืนยันด้วย
`grep` ก่อน แล้วรายงาน — ไม่ใช่สร้างขึ้นมาเอง
ตารางแปลงคำสองชุดคือจุดเริ่มของหน้าจอที่เรียกสิ่งเดียวกันคนละชื่อ

# หมวด ๒ — `driver` ไม่ใช่ `rider` (คำตัดสิน)

Master Guide v2.0 PART 19 ระบุให้ใช้ `Rider` และเลี่ยง `Driver`
**ข้อนี้ถูกยกเลิก** ด้วยเหตุผลที่วัดได้:

การเปลี่ยนชื่อจะกระทบ **RLS policy 5 ข้อ · ฟังก์ชัน 7 ตัว · คอลัมน์ 2 คอลัมน์
· ตาราง `drivers` · ค่า enum · และโค้ด 110 จุดใน 12 ไฟล์** โดยผู้ใช้ไม่เห็น
ความแตกต่างเลยแม้แต่จุดเดียว

```
ในฐานข้อมูลและโค้ด  →  driver   (ตลอดไป)
ในหน้าจอภาษาไทย     →  ไรเดอร์  (ตลอดไป)
```

แปลงคำที่ `ROLE_LABEL` ใน `src/lib/domain.ts` จุดเดียว (ดู ๑.๔)

# หมวด ๓ — กฎว่าด้วยความจริงของเอกสาร (EVIDENCE RULE)

> เหตุที่ต้องมีหมวดนี้: เอกสาร `25-Password-Reset-and-Remember-Me.md`
> เคยประกาศว่าระบบ OTP "✅ Complete (Ready to Integrate)" ทั้งที่โค้ดชุดนั้น
> ไม่เคยถูกเรียกใช้จากที่ไหน เก็บ OTP ไว้ในหน่วยความจำบน serverless
> (ใช้ไม่ได้ตั้งแต่แรก) และไม่มีผู้ให้บริการ SMS อยู่จริง
> ความผิดพลาดนั้นอยู่ในโครงการหลายวันโดยไม่มีใครจับได้

**กฎ ๓.๑** ป้าย `[มีจริงแล้ว]` เขียนได้เฉพาะเมื่อระบุหลักฐานกำกับ อย่างใดอย่างหนึ่ง:
- query ที่รันได้จริง พร้อมผลลัพธ์
- commit hash
- ผลการทดสอบที่ทำจริง โดยระบุว่าทดสอบอะไร

**กฎ ๓.๒** ห้ามใช้ ✅ หรือคำว่า "เสร็จแล้ว/พร้อมใช้" กับสิ่งที่ยังไม่เคยทำงาน
กับข้อมูลจริง — "โค้ดเขียนเสร็จ" ไม่เท่ากับ "ใช้งานได้"

**กฎ ๓.๓** เอกสารที่พบว่าไม่ตรงความจริง **ต้องแก้ทันทีที่พบ** ไม่ใช่รอรอบถัดไป
และต้องเขียนไว้ด้วยว่าเดิมผิดอย่างไร เพื่อไม่ให้คนที่เคยอ่านฉบับเก่าเข้าใจผิดต่อ

**กฎ ๓.๔** ตัวเลขทุกตัวในเอกสารสถานะ ต้องมาจากการ query ระบบจริง
ห้ามคัดลอกตัวเลขจากเอกสารฉบับก่อนหน้า

## ๓.๕ นิยามของคำว่า "เสร็จ" — และเหตุผลที่ต้องมีสองคำ

> เดิม (v2.1) รวมการ deploy ไว้ในนิยามของ "เสร็จ" ข้อเดียว ซึ่งผิด
> เพราะ AI ที่ไม่มีสิทธิ์ deploy จะถูกบังคับให้รายงานว่า "ยังไม่เสร็จ"
> ตลอดไป ทั้งที่ส่วนของมันเสร็จจริง — เป็นการโกหกโดยโครงสร้าง
> v2.2 จึงแยกเป็นสองคำ ที่ห้ามใช้แทนกัน

```
TASK COMPLETE                    FEATURE LIVE
─────────────────                ─────────────────
เขียนแล้ว (มี commit)             TASK COMPLETE ครบ
ทดสอบแล้ว (ระบุว่าทดสอบอะไร)      +
มีหลักฐานบันทึกไว้                deploy ขึ้น production แล้ว
ของเดิมไม่พัง (build/lint ผ่าน)   +
                                 ตรวจแล้วว่าใช้ได้จริงบน production
```

**กฎ ๓.๕.๑** `TASK COMPLETE` คือขอบเขตของผู้ลงมือ
`FEATURE LIVE` คือสิ่งเดียวที่ผู้ใช้ได้ประโยชน์

**กฎ ๓.๕.๒ — ห้ามรายงาน `TASK COMPLETE` ลอย ๆ**
ต้องระบุพร้อมกันเสมอว่า **เหลืออะไรก่อนถึง `FEATURE LIVE` และใครต้องทำ**
เช่น *"TASK COMPLETE — รอเจ้าของโครงการ push ขึ้น GitHub จึงจะ FEATURE LIVE"*

**กฎ ๓.๕.๓** ห้ามใช้คำว่า "เรียบร้อยแล้ว" กับงานที่ยังไม่ `FEATURE LIVE`
โค้ดที่ commit แล้วแต่ยังไม่ deploy ไม่ใช่ฟีเจอร์ เป็นแค่ไฟล์
(เคยเกิดแล้ว: งาน 4 commit — ระบบแจ้งเตือน, ทางกู้คืนรหัสผ่าน, การลบโค้ดตาย —
ค้างอยู่นอก production หลายวัน ขณะที่ผู้ใช้บุ่งไหมยังใช้ของเก่าอยู่)

**กฎ ๓.๕.๔** งานเอกสารมีนิยามของตัวเอง: เขียนแล้ว + ตรวจแล้ว
ไม่ต้องมี `FEATURE LIVE`

# หมวด ๔ — ห้ามรื้อก่อนตรวจ (NO REBUILD WITHOUT AUDIT)

**กฎ ๔.๑** ก่อนแก้หรือลบสิ่งใด ต้องตอบให้ได้ว่า **ใครเรียกใช้มันอยู่**
การตอบต้องมาจากการไล่ dependency จริง ไม่ใช่การเดา

**กฎ ๔.๒** โค้ดที่ไม่มีใครเรียกใช้ ให้ลบ ไม่ใช่เก็บไว้ "เผื่อได้ใช้"
โค้ดตายที่หน้าตาเหมือนของจริงคือกับดัก คนถัดไปจะเชื่อว่ามันทำงาน
(เคยเกิดแล้ว: ไฟล์ต้นแบบตาย 17 ไฟล์ ~150KB ที่ทำให้เชื่อว่าระบบ OTP มีอยู่)

**กฎ ๔.๓** การลบต้องอยู่ใน commit แยก พร้อมเหตุผลว่าทำไมถึงตาย
เพื่อให้ `git revert` กลับได้ในคำสั่งเดียวถ้าคิดผิด

# หมวด ๕ — เปลี่ยนให้น้อยที่สุด (MINIMUM CHANGE)

**กฎ ๕.๑** งานหนึ่งชิ้น = การเปลี่ยนแปลงที่จำเป็นต่องานนั้นเท่านั้น
ห้ามถือโอกาสจัดระเบียบ เปลี่ยนชื่อ หรือ upgrade dependency ไปด้วย

**กฎ ๕.๒** ห้ามแตะ `package.json` / `package-lock.json` โดยไม่มีเหตุผลที่ระบุได้
(เคยเกิดแล้ว: ถอด `lucide-react` ออกเพราะคิดว่าไม่มีใครใช้ ทั้งที่ `wip/` ยังใช้
และ Next bundle เฉพาะโค้ดที่ import อยู่แล้ว การถอดจึงไม่ได้ประโยชน์ใด ๆ)

**กฎ ๕.๓ (STOP RULE)** ถ้าการแก้ปัญหาหนึ่งทำให้ต้องแก้อีกสิบที่ ให้หยุดแล้วรายงานก่อน
นั่นคือสัญญาณว่าเข้าใจปัญหาผิด ไม่ใช่สัญญาณว่าต้องขยันขึ้น

**ข้อยกเว้นเดียวของ ๕.๓** — เมื่อการแตะหลายจุดเกิดจาก **contract เดียวกัน
ที่เปลี่ยนจริง** (เช่นเปลี่ยน signature ของ API หรือฟังก์ชันสิทธิ์)
กรณีนี้ทำต่อได้ แต่ต้อง**ส่งรายการจุดที่กระทบทั้งหมดก่อนลงมือ**
ไม่ใช่ทยอยค้นพบไปเรื่อย ๆ ระหว่างทาง

# หมวด ๖ — กฎการเปลี่ยนฐานข้อมูล (MIGRATION RULES)

**กฎ ๖.๑** ทุกการเปลี่ยนโครงสร้างต้องเป็นไฟล์ migration ใน `supabase/migrations/`
การ apply ผ่านเครื่องมือโดยไม่มีไฟล์คู่กัน **ถือเป็นการละเมิด** — ระบบจะสร้างใหม่
จากศูนย์ไม่ได้ และตำบลที่ ๒ จะเปิดไม่ได้
(เคยเกิดแล้ว: migration สองไฟล์ถูก apply เข้า production ก่อน แล้วต้องย้อนไป
ดึง `pg_get_functiondef()` ออกมาเขียนเป็นไฟล์ทีหลัง)

## ๖.๒ คุณสมบัติที่ migration ต้องมีครบสี่ข้อ

```
VERSIONED     มีลำดับชัดเจน อยู่ในไฟล์ ไม่ใช่ในหัวคน
REPRODUCIBLE  สร้างฐานข้อมูลจากศูนย์ถึงปัจจุบันได้ครบ
RECOVERABLE   มีแผนกู้เขียนไว้ก่อน apply (ดู ๖.๖)
IDEMPOTENT    รันซ้ำแล้วไม่พัง
```

**เหตุผลที่ยังต้องมี IDEMPOTENT ทั้งที่โครงการมี migration history:**
โครงการนี้ apply migration ผ่านหลายทาง (เครื่องมือ MCP และไฟล์) และ
history ฝั่งเราอ่านไม่ได้เสมอไป ไฟล์เดิมจึงถูกรันซ้ำได้จริง
ใช้ `create ... if not exists` และ `drop policy if exists` ก่อน `create policy` เสมอ

**กฎ ๖.๓** ทุกฟังก์ชัน `security definer` ต้องปัก `set search_path`
และต้อง `revoke` จาก `public, anon, authenticated` แล้ว `grant` เฉพาะที่จำเป็น

**กฎ ๖.๔** ห้ามลบคอลัมน์หรือตารางที่มีข้อมูลจริง โดยไม่มีคำสั่งจากเจ้าของโครงการ
เป็นลายลักษณ์อักษรในบทสนทนา

**กฎ ๖.๕** ตารางที่เป็นบันทึกการกระทำ (`admin_actions`, `order_events`)
ต้องไม่มี policy ให้ `authenticated` เขียนหรือลบ — เขียนได้เฉพาะฝั่งเซิร์ฟเวอร์
ผู้ดูแลต้องลบร่องรอยของตัวเองไม่ได้

## ๖.๖ แผนถอย — และเหตุผลที่ "rollback" เป็นคำอันตรายกับฐานข้อมูล

> ถ้า migration เพิ่มคอลัมน์ แล้วผู้ใช้กรอกข้อมูลลงไป 200 แถว
> การ "rollback" คือการลบคอลัมน์นั้น = ทำลายข้อมูลของผู้ใช้ 200 แถว
> การถอยจึงแย่กว่าการอยู่กับปัญหา

**กฎ ๖.๖.๑ — แยกสองกรณี ห้ามปนกัน**

```
โค้ด / การ deploy   →  ถอยได้จริง  (git revert + deploy ใหม่)
โครงสร้างฐานข้อมูล  →  ค่าตั้งต้นคือ "แก้เดินหน้า" ไม่ใช่ถอย
```

**กฎ ๖.๖.๒** ทุก migration ต้องเขียน **แผนกู้** ไว้ในหัวไฟล์ก่อน apply
โดยระบุว่าถ้าผิดจะทำอย่างไร — และคำตอบมักจะเป็น "เขียน migration ตัวถัดไปแก้"
ไม่ใช่ "ถอยตัวนี้"

**กฎ ๖.๖.๓** migration ที่ทำลายได้ (`drop column`, `drop table`, ลบค่า enum,
เขียนทับข้อมูลเดิม) ต้องมีครบสามอย่างก่อน apply:
```
๑. หลักฐานว่าไม่มีอะไรอ่านสิ่งนั้นอยู่แล้ว
๒. แผนกู้ที่เขียนไว้ชัด
๓. คำอนุมัติจากเจ้าของโครงการในบทสนทนา
```

**กฎ ๖.๖.๔** การเลิกใช้คอลัมน์ให้ทำสองจังหวะเสมอ:
```
จังหวะที่ ๑  เลิกอ่าน เลิกเขียน แต่ยังไม่ลบ  → ปล่อยไว้จนแน่ใจ
จังหวะที่ ๒  ค่อยลบ
```
การรวบสองจังหวะเป็นครั้งเดียว คือวิธีทำข้อมูลหายที่พบบ่อยที่สุด

**กฎ ๘.๔** AI ให้คำแนะนำ ไม่ใช่ผู้มีอำนาจตัดสิน

**กฎ ๘.๕** ความล้มเหลวของการแจ้งเตือน ต้องไม่ทำให้การสั่งของล้มเหลว

# หมวด ๑๐ — การจัดระดับการเปลี่ยนแปลง (CHANGE CLASSIFICATION)

ก่อนลงมือทุกครั้ง ต้องบอกให้ได้ว่างานนี้อยู่ระดับไหน

| ระดับ | คืออะไร | ต้องทำอย่างไร |
|---|---|---|
| **A** | เอกสารอย่างเดียว | ทำได้ตามแผน |
| **B** | หน้าจออย่างเดียว ไม่แตะข้อมูล | ทำได้ + ต้องทดสอบ |
| **C** | ตรรกะของแอป | ต้องรายงานผลกระทบก่อน |
| **D** | migration ฐานข้อมูล | ต้องรายงานผลกระทบ + แผนกู้ (๖.๖) |
| **E** | สิทธิ์ / RLS / auth | **หยุด ขออนุมัติก่อน** |
| **F** | ทำลายได้ / ย้อนไม่ได้ / แตะข้อมูลผู้ใช้จริง | **หยุด ขออนุมัติก่อน** |

**กฎ ๑๐.๑** เมื่อไม่แน่ใจว่าอยู่ระดับไหน ให้ถือว่าอยู่ระดับที่สูงกว่า

**กฎ ๑๐.๒** งานหนึ่งชิ้นที่พาดหลายระดับ ให้ยึดระดับสูงสุดเป็นเกณฑ์
เช่นแก้หน้าจอ (B) แต่ต้องแก้ policy ด้วย (E) → ทั้งชิ้นเป็น E

**กฎ ๑๐.๓** ระดับ E และ F ต้อง**แยก commit** ออกจากงานอื่นเสมอ

## ๑๐.๔ ผลกระทบต่อ production เป็นอีกมิติหนึ่ง ไม่ใช่ระดับ

ระดับ A–F บอกว่างาน**อันตรายแค่ไหน** แต่ไม่ได้บอกว่า**ผู้ใช้จะเจออะไร**
งานระดับ B ที่ deploy ผิดจังหวะก็ทำให้ทั้งเว็บล่มได้

**กฎ ๑๐.๔.๑** งานใดที่จะถูก deploy ขึ้น production ต้องรายงานเพิ่มว่า:
```
ผู้ใช้จะเห็นอะไรเปลี่ยนไป
มีอะไรที่เคยใช้ได้แล้วอาจใช้ไม่ได้
ถ้าพังจะรู้ได้อย่างไร และภายในกี่นาที
```
ไม่ว่าจะเป็นระดับ A หรือ F ก็ตาม

# หมวด ๑๒ — เมื่อเอกสารขัดกับระบบจริง

> หมวดนี้กลับหัวความผิดพลาดของเอกสาร 25 ให้เป็นกฎถาวร

**กฎ ๑๒.๑ — ระบบจริงชนะเอกสารเสมอ ในเรื่องข้อเท็จจริง**
เมื่อเอกสาร (แม้แต่ Constitution ฉบับนี้) ระบุว่าระบบเป็นอย่าง A
แต่ระบบจริงเป็น B **ห้ามแก้ระบบให้เป็น A ทันที**

```
พบความขัดแย้ง
      ↓
รายงานพร้อมหลักฐานว่าของจริงเป็นอย่างไร
      ↓
เจ้าของโครงการตัดสิน
      ↓
      ├── เอกสารผิด  →  แก้เอกสาร
      └── ระบบผิด    →  แก้ระบบ (จัดระดับตามหมวด ๑๐ ก่อน)
```

## ๑๒.๒ แยกให้ออกระหว่าง "ข้อเท็จจริง" กับ "เจตนา"

**ชื่อหรือตัวเลขไม่ตรง = ข้อเท็จจริง** → เอกสารมักผิด แก้เอกสาร
(เอกสารบอกว่ามีตาราง `areas` แต่จริง ๆ ชื่อ `tambons`)

**หลักการไม่ตรง = ต้องสืบก่อน ห้ามสรุปว่าโค้ดผิดทันที**
เอกสารบอกห้ามเขียนตรรกะสิทธิ์ซ้ำ แต่โค้ดเขียนซ้ำอยู่ — อาจเป็นได้สามอย่าง:

```
๑. โค้ดผิดจริง                        →  แก้โค้ด
๒. เจ้าของเคยตัดสินใจไว้ แต่ไม่ได้บันทึก  →  แก้เอกสารให้บันทึกไว้
๓. มีข้อจำกัดทางเทคนิคที่เอกสารไม่รู้     →  แก้เอกสารให้รับรู้ข้อจำกัด
```

**ต้องรายงานทั้งสามความเป็นไปได้ แล้วให้เจ้าของโครงการเลือก**
Constitution สูงกว่าโค้ดตามลำดับอำนาจก็จริง แต่ Constitution เขียนโดยคน
ที่อาจไม่รู้ข้อจำกัดหน้างาน — และระบบจริงอาจสะท้อนการตัดสินใจล่าสุด
ที่ยังไม่ทันเขียนลงเอกสาร

**กฎ ๑๒.๓** ห้ามแก้ระบบที่ทำงานได้อยู่ เพียงเพราะเอกสารบรรยายไว้ต่างออกไป
เอกสารเขียนง่ายกว่าระบบ จึงผิดง่ายกว่าระบบ

การแก้ต้องระบุ: ข้อไหน · เปลี่ยนเป็นอะไร · เพราะเกิดอะไรขึ้นจริง

**กฎที่มาจากความผิดพลาดจริง ห้ามลบโดยไม่มีหลักฐานว่าปัญหานั้นหมดไปแล้ว**
ข้อที่มีวงเล็บ "(เคยเกิดแล้ว: ...)" คือข้อที่ซื้อมาด้วยความเสียหายจริง
